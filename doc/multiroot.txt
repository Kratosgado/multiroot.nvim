==============================================================================
1. INTRODUCTION                                         *multiroot-introduction*

`multiroot.nvim` groups N folders into a single Neovim workspace, declared in
a JSON file. Once a workspace is loaded:

  - every LSP client sees all folders as workspace roots
  - fuzzy-find and live-grep span every folder
  - long-running terminals (dev servers, watchers) and one-shot tasks (build,
    test, deploy) are declared in the workspace file
  - task stacks launch a named group of tasks in one shot, arranged as tabs,
    columns, or a grid
  - per-project Ex commands and keymaps declared in the workspace file,
    registered on open and removed on close
  - env vars are set on open, restored on close
  - shell hooks run when the workspace opens and when it closes or Neovim exits
  - named env profiles can be layered onto individual terminals/tasks
  - sessions save/restore per workspace
  - closing or switching wipes the workspace's buffers and terminals

==============================================================================
2. REQUIREMENTS                                         *multiroot-requirements*

  - Neovim 0.9+ (0.11+ for `settings.lsp` overrides)
  - Optional: snacks.nvim or fzf-lua (for :WorkspaceFiles / :WorkspaceGrep)
  - Optional: snacks.nvim for a nicer terminal backend (falls back to built-in
    :terminal in a bottom split)

3. SETUP                                                        *multiroot-setup*

With lazy.nvim: >lua

  {
    "multiroot.nvim",
    dir = "~/projects/configs/multiroot.nvim",
    event = "VeryLazy",
    opts = {
      keys_when_active = {
        { "<leader>qc", "<cmd>WorkspaceClose<cr>",     desc = "Close" },
        { "<leader>qf", "<cmd>WorkspaceFiles<cr>",     desc = "Files" },
        { "<leader>qg", "<cmd>WorkspaceGrep<cr>",      desc = "Grep" },
        { "<leader>qe", "<cmd>WorkspaceEdit<cr>",      desc = "Edit ws file" },
        { "<leader>qt", "<cmd>WorkspaceTerm<cr>",      desc = "Terminal" },
        { "<leader>qT", "<cmd>WorkspaceTermRun<cr>",   desc = "Named term" },
        { "<leader>qx", "<cmd>WorkspaceTask<cr>",      desc = "Task" },
      },
    },
    keys = {
      { "<leader>qo", "<cmd>WorkspaceOpen<cr>",   desc = "Open workspace" },
      { "<leader>qr", "<cmd>WorkspaceRecent<cr>", desc = "Recent" },
    },
  }
<

Or from Lua directly: >lua

  require("multiroot").setup({})
<

4. WORKSPACE FILE                                     *multiroot-workspace-file*

A workspace is a JSON file, conventionally named `.nvim-workspace.json` at the
parent directory of your repos. When `nvim` is launched in a directory that
contains this file, the workspace is loaded automatically.

Full example: >

  {
    "name": "acme",
    "folders": [
      "~/projects/acme-frontend",
      "~/projects/acme-backend"
    ],
    "terminals": [
      { "name": "backend", "folder": "acme-backend",
        "cmd": "npm run dev", "env": "dev", "autostart": true }
    ],
    "tasks": [
      { "name": "build",  "folder": "acme-backend", "cmd": "make",
        "description": "Compile the backend" },
      { "name": "test",   "folder": "acme-backend", "cmd": "pytest -q",
        "description": "Run unit tests" },
      { "name": "deploy", "cmd": "./deploy.sh",     "env": "prod",
        "description": "Deploy to production" }
    ],
    "stacks": [
      { "name": "dev", "description": "Backend + frontend side-by-side",
        "tasks": ["backend", "build"], "layout": "columns" },
      { "name": "ci",  "tasks": ["build", "test"], "layout": "tabs" }
    ],
    "commands": [
      { "name": "AcmeDeploy", "action": "task:deploy", "desc": "Deploy acme" },
      { "name": "AcmeDev",    "action": "stack:dev",   "desc": "Start dev stack" },
      { "name": "AcmeGreet",  "action": "lua:vim.notify('hello from acme!')" }
    ],
    "keymaps": [
      { "lhs": "<leader>ad", "rhs": ":WorkspaceTask deploy<CR>", "mode": "n",
        "desc": "Acme: deploy" },
      { "lhs": "<leader>as", "rhs": ":WorkspaceStack dev<CR>",   "mode": "n",
        "desc": "Acme: dev stack" }
    ],
    "env": {
      "AWS_PROFILE": "acme-dev"
    },
    "envs": {
      "dev":  { "API_URL": "http://localhost:3000" },
      "prod": { "API_URL": "https://api.acme.com" }
    },
    "settings": {
      "lsp": {
        "pyright": {
          "settings": {
            "python": { "pythonPath": "./venv/bin/python" }
          }
        }
      }
    }
  }
<

------------------------------------------------------------------------------
4.1 folders                                                  *multiroot-folders*

Array of paths (absolute or with `~`). Neovim `cd`s into the first folder on
open. All folders become LSP workspace roots.

------------------------------------------------------------------------------
4.2 terminals                                              *multiroot-terminals*

Long-running processes. Each entry:

  name      required. Referenced by :WorkspaceTermRun and tracked per
            workspace — re-running focuses the existing buffer.
  folder    basename (matched against `folders`) or absolute path. Defaults
            to the first workspace folder.
  cmd       shell command. Omit for a plain shell. Commands run through an
            interactive shell ($SHELL -ic), so PATH/aliases exported from
            your rc file are available — same environment as a terminal you
            open by hand.
  env       optional profile name from `envs`; those vars are added to the
            spawned process.
  position  passed to the terminal backend ("bottom", "float", etc.).
  autostart if true, launch on workspace open (see |g:multiroot-terminal|
            config).

------------------------------------------------------------------------------
4.3 tasks                                                      *multiroot-tasks*

One-shot commands run in a fresh terminal split each time. No autostart, no
buffer reuse. Fields match `terminals` except no `autostart`, plus:

  description  optional. Shown in the |:WorkspaceTask| picker instead of the
               raw `cmd`, so the picker stays readable with long commands.

------------------------------------------------------------------------------
4.4 stacks                                                    *multiroot-stacks*

A stack is a named group of tasks launched together in one shot. Fields:

  name         required.
  tasks        required. Ordered list of task names defined in this file.
  layout       how to arrange the terminal windows:
               "tabs"    (default) one tab per task; navigate with gt / gT
               "columns" all tasks side-by-side in one tab
               "grid"    tasks in pairs per tab (two columns per page);
                         e.g. 6 tasks → 3 tabs of [t1|t2], [t3|t4], [t5|t6]
  description  optional. Shown in the |:WorkspaceStack| picker.

Run a stack interactively: |:WorkspaceStack| (picker if no arg).
Run from Lua: `require("multiroot").stack(name?)`.

------------------------------------------------------------------------------
4.5 commands                                          *multiroot-project-commands*

Per-project Ex commands registered when the workspace opens and deleted when
it closes. Each entry:

  name    required. The Ex command name (e.g. `"AcmeDeploy"`). Must follow
          the usual user-command naming rules (see |:command|).
  action  required. One of:
          "task:<name>"   run the named task from this workspace
          "stack:<name>"  run the named stack from this workspace
          "lua:<code>"    evaluate arbitrary Lua (e.g. "lua:vim.notify('hi')")
  desc    optional. Description shown by |:command| and which-key.

Commands are registered on |MultirootLoaded| and deleted on |MultirootClosed|.
If the same command name is already registered, registration is silently
skipped for that entry.

Because `lua:` can run arbitrary code, this has the same trust model as
|:h exrc|.

------------------------------------------------------------------------------
4.6 keymaps                                                  *multiroot-keymaps*

List of workspace-scoped keymaps registered on open, removed on close.

  "keymaps": [
    { "lhs": "<leader>rt", "rhs": "<cmd>WorkspaceTask test<cr>",   "desc": "run tests" },
    { "lhs": "<leader>rd", "rhs": "<cmd>WorkspaceTask deploy<cr>", "mode": "n",
      "desc": "deploy" },
    { "lhs": "<leader>rs", "rhs": "<cmd>WorkspaceStack dev<cr>",   "mode": "n",
      "desc": "dev stack" }
  ]

Fields:

  lhs   required. Key sequence to bind.
  rhs   required. Ex command / key sequence. Same syntax as |vim.keymap.set|.
  mode  optional. String or list of modes. Defaults to "n".
  desc  optional. Description shown in which-key / |:map|.

Keymaps are registered on |MultirootLoaded| and removed on |MultirootClosed|.
These live in the shared workspace file, so all team members get the same
project-specific bindings. Because `rhs` can be any Ex command, this has the
same trust model as |:h exrc|. Disable via: >lua

  require("multiroot").setup({
    workspace_keymaps = { enabled = false },
  })
<

Separate from `keys_when_active` in setup opts — that lives in your personal
Neovim config; `keymaps` in the JSON lives with the project.

Use `keymaps` to bind tasks and stacks to keys without consuming global keymap
slots. Use |multiroot-project-commands| when you want named Ex commands you can
tab-complete or call from scripts rather than (or in addition to) key bindings.

------------------------------------------------------------------------------
4.7 env / envs                                                  *multiroot-env*

`env` is the always-on base map. Applied to |vim.env| on workspace open
(previous values are snapshotted); restored on close.

`envs` is a map of named profiles. Reference from a terminal or task via
`"env": "<name>"`. Those vars flow only into the spawned child process —
Neovim's own `vim.env` stays on the base. This means two terminals with
different profiles can run at once.

------------------------------------------------------------------------------
4.8 settings.lsp                                       *multiroot-lsp-settings*

Per-server config patch. Keys are LSP server names; values are merged into
|vim.lsp.config| for that server. Attached clients are notified via
`workspace/didChangeConfiguration`. Reverted on close.

Requires Neovim 0.11+.

------------------------------------------------------------------------------
4.9 hooks                                                      *multiroot-hooks*

Shell commands run around the workspace lifecycle: >

  "hooks": {
    "on_open": [
      "docker compose up -d",
      { "name": "migrate", "folder": "acme-backend",
        "cmd": "npm run migrate", "env": "dev" }
    ],
    "on_close": ["docker compose down"]
  }
<
Each entry is a command string or an object:

  cmd     required. Run via 'shell' -c.
  name    optional. Label used in notifications instead of the raw cmd.
  folder  optional. Folder basename or absolute path. Defaults to the first
          workspace folder.
  env     optional. Env profile from `envs` layered onto the command.

on_open   Runs in the background when the workspace opens, including at
          startup with `auto_load`. Not awaited: `autostart` terminals start
          alongside the hooks.
on_close  Runs to completion (blocking) when the workspace is closed, when
          switching to another workspace, and when Neovim exits with a
          workspace open.

Entries run in order. A failing entry is reported and the rest still run; use
`&&` inside a single `cmd` when steps depend on each other. Each command is
killed after `hooks.timeout` ms (default 30000). |:WorkspaceReload| does not
re-run hooks, so services they manage are left alone.

Hooks run arbitrary shell commands, so this has the same trust model as
|:h exrc|. Disable via: >lua

  require("multiroot").setup({
    hooks = { enabled = false },
  })
<
Requires Neovim 0.10+ (`vim.system`).

==============================================================================
5. COMMANDS                                                 *multiroot-commands*

                                                              *:WorkspaceOpen*
:WorkspaceOpen [file]     Open a workspace by path, or (with no arg) pick
                          from recent workspaces.

                                                             *:WorkspaceClose*
:WorkspaceClose           Close the active workspace. Saves the session,
                          restores env, removes LSP folders, wipes workspace
                          buffers and terminals (see |multiroot-close|).

                                                              *:WorkspaceEdit*
:WorkspaceEdit            Open the current workspace's JSON file.

                                                            *:WorkspaceCreate*
:WorkspaceCreate [folders...]
                          Create `.nvim-workspace.json` at the current working
                          directory. Folders default to cwd if none given.
                          Errors if the file already exists (use
                          |:WorkspaceEdit|). Auto-opens the workspace on
                          success.

                                                            *:WorkspaceReload*
:WorkspaceReload          Re-read the current workspace file from disk and
                          re-apply state. Handy after editing the file via
                          |:WorkspaceEdit|.

                                                               *:WorkspaceGit*
:WorkspaceGit             Open the configured git tool at the current buffer's
                          workspace folder. Defaults to Neogit when installed;
                          override via `opts.git.open`. Useful in multi-root
                          workspaces where the git tool would otherwise open
                          on the workspace's primary folder regardless of the
                          buffer you're editing.

                                                         *:WorkspaceAddFolder*
:WorkspaceAddFolder [dir] Add a folder to the active workspace and write it
                          back to disk.

                                                      *:WorkspaceRemoveFolder*
:WorkspaceRemoveFolder {dir}
                          Remove a folder from the active workspace.

                                                              *:WorkspaceList*
:WorkspaceList            Print the active workspace's name, file, and
                          folders.

                                                            *:WorkspaceRecent*
:WorkspaceRecent          Pick from recent workspaces.

                                                             *:WorkspaceFiles*
:WorkspaceFiles           Fuzzy-find files across every workspace folder.

                                                              *:WorkspaceGrep*
:WorkspaceGrep            Live-grep across every workspace folder.

                                                              *:WorkspaceTerm*
:WorkspaceTerm [folder]   Open a terminal cd'd to a workspace folder. Picker
                          if omitted (or first folder if only one).

                                                           *:WorkspaceTermRun*
:WorkspaceTermRun [name]  Launch (or focus) a named terminal declared in the
                          workspace file. Picker if omitted.

                                                          *:WorkspaceTermList*
:WorkspaceTermList        List named terminals declared in the workspace.

                                                              *:WorkspaceTask*
:WorkspaceTask [name]     Run a task. Picker if omitted.

                                                          *:WorkspaceTaskList*
:WorkspaceTaskList        List workspace tasks with their folder and command.

                                                             *:WorkspaceStack*
:WorkspaceStack [name]    Run a stack (launches all of its tasks in the
                          configured layout). Picker if omitted.

                                                         *:WorkspaceStackList*
:WorkspaceStackList       List workspace stacks with their task members and
                          layout.

                                                       *:WorkspaceSaveSession*
:WorkspaceSaveSession     Force save the current workspace session.

                                                       *:WorkspaceLoadSession*
:WorkspaceLoadSession     Restore the active workspace's session from disk.

6. CONFIGURATION                                       *multiroot-configuration*

`setup()` accepts a table merged over these defaults: >lua

  require("multiroot").setup({
    workspace_file = ".nvim-workspace.json",
    data_dir = vim.fn.stdpath("data") .. "/multiroot",
    auto_load = false,           -- auto-open on VimEnter in cwd
    session = {
      enabled = true,
      autosave = true,          -- on VimLeavePre
      autoload = true,          -- on WorkspaceOpen
    },
    lsp = {
      enabled = true,           -- multi-root LSP + settings overrides
    },
    picker = "auto",            -- "snacks" | "fzf" | "auto"
    notify = true,
    keys_when_active = {},      -- see |multiroot-keys-when-active|
    terminal = {
      autostart = true,         -- run autostart terminals on open
    },
    on_close = {
      wipe_buffers = true,      -- delete file buffers under ws folders
      close_terminals = true,   -- kill named terminals for the workspace
    },
    hooks = {
      enabled = true,           -- run the workspace file's `hooks` (|multiroot-hooks|)
      timeout = 30000,          -- ms before one hook command is killed
    },
  })
<

                                                    *multiroot-keys-when-active*
`keys_when_active` is a list of keymap specs registered when a workspace
loads and removed when it closes. Each entry is `{lhs, rhs, opts...}` — the
same shape as |vim.keymap.set()| entries. Optional `mode` (defaults to "n").

Example: >lua

  keys_when_active = {
    { "<leader>qf", "<cmd>WorkspaceFiles<cr>", desc = "files" },
    { "<C-/>",      "<cmd>WorkspaceTerm<cr>",  desc = "terminal", mode = { "n", "t" } },
  }
<

7. LUA API                                                       *multiroot-api*

>lua
  local mr = require("multiroot")

  mr.setup(opts)
  mr.open(path)                -- open a workspace file
  mr.close()                   -- close current workspace
  mr.create(folders?, name?)   -- always at cwd/<workspace_file>
  mr.reload()                  -- re-read the current workspace file
  mr.folder_for_buffer(bufnr?) -- absolute path of the buffer's owning folder
  mr.git(bufnr?)               -- open the configured git tool at that folder
  mr.add_folder(path)
  mr.remove_folder(path)
  mr.current()                 -- workspace table or nil
  mr.folders()                 -- list of active folder paths
  mr.files()                   -- open files picker
  mr.grep()                    -- open grep picker
  mr.recent()                  -- open recent-workspaces picker
  mr.terminal(folder?)         -- terminal in folder (picker if nil)
  mr.terminal_run(name?)       -- launch/focus a named terminal
  mr.task(name?)               -- run a task (picker if nil)
  mr.stack(name?)              -- run a stack (picker if nil)
  mr.edit()                    -- open the current workspace file
  mr.statusline(opts?)         -- statusline string; opts = { icon, folder, bufnr }
<

8. EVENTS                                                     *multiroot-events*

`User` autocmds fired on state changes:

                                                        *MultirootLoaded*
MultirootLoaded          After opening a workspace. `args.data` is the
                         workspace table.

                                                        *MultirootClosed*
MultirootClosed          After closing a workspace. `args.data` is the
                         workspace table that was closed.

Example: >lua

  vim.api.nvim_create_autocmd("User", {
    pattern = "MultirootLoaded",
    callback = function(args)
      print("opened workspace:", args.data.name)
    end,
  })
<

9. STATUSLINE                                             *multiroot-statusline*

>lua
  -- lualine
  sections = {
    lualine_c = {
      { function() return require("multiroot").statusline() end },
    },
  }
<

Returns `" acme:backend"` when a workspace is open, empty string otherwise.
The folder segment is the deepest workspace folder containing the current
buffer's file.

Options: >lua

  require("multiroot").statusline({
    icon = true,     -- show the leading icon (default true)
    folder = true,   -- append :folder segment (default true)
    bufnr = 0,       -- resolve folder for a specific buffer
  })
<

Also exposed: >lua

  require("multiroot.statusline").name()       -- just the workspace name
  require("multiroot.statusline").folder(buf)  -- just the folder segment
<

10. CLOSE / SWITCH BEHAVIOR                                    *multiroot-close*

`:WorkspaceClose` (and opening a workspace on top of an active one) does the
following, in order:

  1. Save the workspace session (if `session.autosave` is enabled)
  2. Kill named terminals for the workspace (`on_close.close_terminals`)
  3. Run `hooks.on_close` and wait for them (|multiroot-hooks|). Also run
     when Neovim exits with a workspace open.
  4. Wipe file buffers whose path is under any workspace folder
     (`on_close.wipe_buffers`) — modified buffers are kept and counted
  5. Revert `settings.lsp` overrides
  6. Remove each folder from every attached LSP client
  7. Restore env vars
  8. Fire |MultirootClosed|

Buffers outside the workspace (help, scratch, unrelated files) are untouched.

11. GIT INTEGRATION                                             *multiroot-git*

|:WorkspaceGit| opens the configured git tool at the buffer's owning workspace
folder. This solves the multi-root case where a cwd-based tool (Neogit,
lazygit, fugitive) would otherwise always show the workspace's primary folder
regardless of the file you're editing.

Configure the tool via `opts.git.open`: >lua

  require("multiroot").setup({
    git = {
      open = function(cwd)
        require("neogit").open({ cwd = cwd })
        -- or: require("snacks").terminal.open("lazygit", { cwd = cwd })
        -- or: vim.cmd("cd " .. vim.fn.fnameescape(cwd) .. " | Git")
      end,
    },
  })
<

The default `open` calls Neogit when it's installed.

For workflows where you want *every* cwd-based tool to Just Work (not just
git), enable auto-lcd: >lua

  require("multiroot").setup({
    on_buf_enter = { lcd = true },
  })
<

This installs a `BufEnter` autocmd that sets the window-local cwd (see |lcd|)
to the buffer's owning workspace folder. `:!git status`, `:terminal`, and any
plugin that reads `getcwd()` will then follow you as you switch between files
in different folders. Off by default because it also changes what
`:e some/path` resolves to and can surprise users who rely on a stable cwd.

12. JSON SCHEMA                                              *multiroot-schema*

The plugin ships a JSON schema at `schemas/workspace.json` describing every
valid field of a workspace file. On `setup()`, it is auto-registered with
`jsonls` (if configured) so editing `.nvim-workspace.json` gets completion,
hover, and validation for free.

Disable auto-registration if you manage jsonls schemas yourself: >lua

  require("multiroot").setup({
    schema = { register = false },
  })
<

Get the on-disk path for manual registration (SchemaStore.nvim, custom
setups, other language servers): >lua

  require("multiroot").schema_path()
<

Example manual jsonls config: >lua

  vim.lsp.config("jsonls", {
    settings = {
      json = {
        schemas = {
          {
            fileMatch = { ".nvim-workspace.json" },
            url = "file://" .. require("multiroot").schema_path(),
          },
        },
        validate = { enable = true },
      },
    },
  })
<

==============================================================================
13. HEALTH CHECK                                              *multiroot-health*

`:checkhealth multiroot` reports:
  - Neovim version compatibility
  - Whether a workspace is active, and each folder's existence
  - Which picker backend was detected (snacks / fzf-lua)
  - Which terminal backend is in use
  - Whether the data directory exists
